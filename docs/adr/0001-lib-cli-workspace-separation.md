# 0001: lib/cliワークスペース分離と責任分担

## 日付

2026-01（初期開発時に決定）

## ステータス

承認済み（Accepted）

## コンテキスト

.nksfファイル（Native Instruments Massive Xのプリセット形式）を解析するRustプロジェクトを新規に立ち上げるにあたり、コードをどのように構成するかを決める必要があった。想定される利用形態は次の2つである。

1. **ライブラリとしての利用**: .nksfファイルのバイト列を解析し、Rustの構造体としてデータを取り出したい。利用者は独自の方法（任意のシリアライザ、DB格納、GUIなど）で結果を扱う。
2. **CLIツールとしての利用**: コマンドラインから .nksf ファイルを解析し、人間や他ツールが扱えるJSONとして出力したい。

解析処理（RIFFコンテナの走査、MessagePackのデシリアライズ、チャンクごとの構造化）と出力処理（JSONへのシリアライズ、オプション解釈、ファイル書き出し）は、変更の理由が異なる関心事である。1つのクレートに混在させると、ライブラリ利用者は不要なJSON出力機能まで引き込まれる。

## 決定

Cargoワークスペースで2つのクレートに分離する。

- **`lib`（`nksf-parser`）**: 純粋なパーサーライブラリ。RIFF/MessagePackの解析のみを行い、`NksfFile`等の構造化されたデータを返す。**JSON出力は一切行わない**。JSON向けの出力最適化も行わない。
- **`cli`（`nksf-parser-cli`）**: コマンドラインインターフェース。引数処理、`nksf-parser`による解析実行、JSONシリアライズとファイル/stdout出力、エラーメッセージのユーザー向け装飾を担う。

```
CLI Layer (cli)
  - 引数処理 / JSON出力 / UX
        │ 依存
        ▼
Parser Library (lib)
  - RIFF解析 / MessagePackデシリアライズ / データ構造定義
```

依存方向は `cli → lib` の一方向とし、`lib` は `cli` やプレゼンテーション層に依存しない。

## 理由

- **責任の分離**: 解析ロジックと出力ロジックは変更理由が異なる。分離により互いに影響せず進化できる。
- **ライブラリ利用者の自由の保護**: ライブラリ側にJSON出力を持たせないことで、ライブラリ利用者はserde_json固有の出力形状に縛られない。構造体には`Serialize`/`Deserialize`を導出するが、具体的なフォーマットの選択は利用者に委ねられる。
- **JSON出力ロジックのCLI側への集約**: JSONへの整形・出力（pretty-print、JSONL結合など）はCLIに閉じ込める。libでも`serde_json::Value`を生データ保持のために使用する（`NiInternal`、PCHK `values` 等）が、これは出力形式としてのJSONではなく、型未規定データのコンテナとしての利用である（[messagepack-encoding.md](../specs/messagepack-encoding.md) 参照）。
- **テスト戦略の明確化**: パーサーの正しさ（全バイト解析）とCLIの振る舞い（出力形式・オプション）を独立にテストできる。

## 影響 / 結果

- ワークスペースは `members = ["lib", "cli"]` で構成され、共通設定（バージョン、edition、lints）は `[workspace.package]` / `[workspace.lints]` に集約される。
- 「JSONが欲しい場合はCLIを使うか、自身でシリアライズする」というAPI契約が明確になった。
- CLIの追加要件（複数ファイル対応、JSONL対応など）はすべて `cli` 側の変更で完結し、`lib` のAPI安定性を損なわない。
- リント方針（clippy all+pedantic を警告レベルで有効化、`unsafe_code` の禁止）をワークスペースレベルで両クレートに統一適用している。

## 代替案

- **単一クレート + featureフラグ**: `json` featureでserde_json依存と出力関数を切り替える案。クレート数が増えない利点があるが、featureの組み合わせ管理（デフォルト/JSON有効/CLI有効）が複雑になり、「libはJSON出力を行わない」という責任境界がコンパイル時の切り替えに埋もれて曖昧になるため不採用。
- **3クレート構成（core / parser / cli）**: 解析をさらに分割する案。現状のパーサーの規模では分割する実益がなく、管理コストだけが増えるため不採用。

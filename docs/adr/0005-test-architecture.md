# 0005: テストアーキテクチャ（rstest + insta スナップショット基盤）

## 日付

2026-01（決定）。当初の期待値生成方式は同年にスナップショット方式へ置き換えられ、本ADRとして確定した。

## ステータス

承認済み（Accepted）

## コンテキスト

Massive X Factory Libraryの**全720プリセット**をfixtureとして、各プリセットの全フィールド・全値を検証する統合テストが必要である。要件上、「パースできること」の確認だけでなく、解析結果そのものが正しいことの継続的な保証が求められる。

当初採用していた方式（第1世代）は次の通りだった。

- プリセットごとに `*_expected_data.rs` を自動生成（720ファイル、合計約400MB）
- 期待値は `phf::Map` ベースの静的データとしてRustソースに埋め込み
- 生成スクリプト群（generators）で期待値ファイル・モジュール宣言・テスト関数を生成

この方式は実行速度に優れていた一方で、深刻な問題を抱えていた。

- **コンパイル時間とバイナリサイズへの重圧**: 400MB超のRustソースを毎回コンパイルする。
- **モジュール参照の複雑さ**: testsディレクトリ配下の独立テストクレート間での参照制約により、720モジュールの取り回しが脆い。
- **保守コスト**: 差分レビューがRustコードのdiffになり、人間が追跡しにくい。生成物と手書きコードの境界も不明瞭になりがち。

## 決定

テストスタックを以下のように再構成する。fixtureテストの期待値保持は **phf静的データからinstaスナップショットへ全面移行**する。

| ツール | 役割 |
|--------|------|
| **rstest** | 720プリセットを1つのテスト関数の`#[case]`としてパラメータ化 |
| **insta**（yaml feature） | 解析結果全体をYAMLスナップショット化。`insta::assert_yaml_snapshot!`を使用 |
| **cargo-nextest** | テストランナー。CIでも使用 |
| **pretty_assertions** | 失敗時の可読性の高いdiff表示（`assert_eq!`のドロップイン置換） |
| **proptest** | プロパティベーステスト。「任意のバイト列でパーサーがパニックしない」「有効なRIFFヘッダ＋任意ペイロードでもパニックしない」を検証 |
| **criterion** | パース処理のベンチマーク（`lib/benches/parser_bench.rs`） |

現在のfixtureテストの形態:

- `lib/tests/fixture_test.rs` に `#[case("Abandoned")]` 等の720エントリを列挙
- 各ケースはプリセットをパースし `insta::assert_yaml_snapshot!` で検証
- スナップショット（.snap、YAML形式、約380MB）は `lib/tests/snapshots/` 配下に置き、Gitにコミットする
- 変更時は `cargo insta review` で差分を対話的に確認・承認できる
- fixtureの .nksf バイナリ自体はGitにコミットせず、オブジェクトストレージからアーカイブ（7z）で取得し、sha256による完全性検証を行う（`lib/tests/checksum.sha256` に個別ファイルのハッシュを管理、`.github/workflows/ci.yml` でダウンロード・検証・展開）

## 理由

- **スナップショットは人間がレビュー可能な形式**: YAML diffは「どのフィールドがどう変わったか」を直接読める。phf版のRustコードdiffより認知負荷が低い。
- **コンパイル時間からの解放**: 期待値がデータファイルになるため、400MBのRustソースのコンパイルが不要になる。
- **テストコードの劇的な簡素化**: 720個のテスト関数が1つの`#[case]`付き関数になる。新規プリセット追加は`#[case]`1行とスナップショット生成のみ。
- **instaの承認ワークフロー**: 意図しない差分はreviewで棄却でき、意図した変更だけを確定できる。
- **nextest**: 並列実行と出力の分離により、大量ケースの実行が高速かつ読みやすくなる。
- **proptestの位置づけ**: セキュリティ対策（[ADR 0004](0004-resource-limits-for-dos-protection.md)）の効果を含め、「パーサーは入力によらずパニックしない」という不変条件を汎用的に検証する。
- **fixture非コミットの理由**: 数百MBのバイナリをGitに入れるとcloneやdiffの性能を損なう。sha256検証付きの取得フローで同じ再現性を確保する。

## 影響 / 結果

- 全759テスト（ユニット32 + 統合7 + fixture 720）がnextestで実行され、すべて成功している。
- スナップショット約380MBはGitにコミットされる。これは「期待値の変更履歴をGitで追える」ことを優先した判断であり、レビュー時にはsnapshot差分がPR上で直接見える。
- パーサーの挙動を変える変更は必ずスナップショット差分として可視化されるため、意図しない解析結果の変化を見逃しにくい。逆に、意図した変更では大量の`.snap.updated`を承認する作業が発生する。
- 第1世代の生成スクリプト・expected_data.rs・phf依存は廃止された（dev-dependenciesのphfは過渡期の名残で残存）。
- CIはfixturesのダウンロード（オブジェクトストレージ + sha256検証）→ `cargo fmt --check` → clippy → `cargo nextest run` の順で実行される。

## 代替案

- **phfベース期待値の継続（第1世代の維持）**: 実行時コストゼロという利点があるが、コンパイル時間・保守性・レビュー性の問題が解消できないため廃止。
- **JSON等の外部データファイルを自前ロードする方式**: 実行時にパースが必要で、比較ロジックも自作になる。instaが同等機能を提供済みのため不採用。
- **標準テストランナーのまま運用**: 720ケースの実行時間と出力可読性の点でnextestに劣るため不採用（`cargo test`も互換性確認用に引き続き動作する）。
- **golden master をバイナリ（例: serde_jsonでシリアライズ）で保存**: 人間がdiffを読めないため不採用。YAMLを選択したのは可読性のためである。

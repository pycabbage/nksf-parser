# 0004: DoS攻撃防御のためのリソース上限

## 日付

2026-01（初期開発時に決定）

## ステータス

承認済み（Accepted）

## コンテキスト

本パーサーは**信頼されていない入力**（任意の .nksf ファイル、あるいは拡張子だけ偽った任意ファイル）を解析対象とする。CLIはバッチ処理での使用も想定しており、1つの悪意あるファイルがプロセス全体を停止させたりメモリを枯渇させたりしてはならない。

考慮すべき攻撃面は以下の通りである。

- **巨大チャンクサイズの申告**: RIFFヘッダにはチャンクサイズが32ビットで記録される。不正なファイルが「4GBのチャンク」と申告した場合、それに従ってバッファを確保しようとするとOOMでクラッシュする。
- **Zipボム（展開爆弾）**: PCHKチャンクはzlib圧縮されている。実際のプリセットの圧縮率は約16倍程度だが、圧縮データからは展開後サイズを事前に知ることはできず、悪意のあるファイルは膨大な展開結果を返せる。
- **値数の爆発**: PCHKの展開後データはMessagePack値の連続として読まれる。極端に小さな値（例: nil）を大量に詰め込めば、値の個数ベースでメモリと時間を浪費できる。

また、構文的に正しいが意味的に不正なファイルに対する検証も必要だった。必須メタデータが空文字列であるケースや、パラメータIDの重複は、解析成功後に下流ツールが誤動作する原因になる。

## 決定

パーサーに以下のリソース上限とバリデーションを設ける。

### リソース上限

| 上限 | 値 | 適用箇所 | 超過時 |
|------|-----|----------|--------|
| `MAX_CHUNK_SIZE` | 100MB | riff_reader — チャンクデータ読み取り前のサイズチェック | エラー |
| `MAX_DECOMPRESSED_SIZE` | 50MB | pchk_parser — zlibデコーダーに`take()`で接続し、読み取り量そのものを制限 | エラー |
| `MAX_MSGPACK_VALUES` | 100,000 | pchk_parser — MessagePack値のループごとにカウント | エラー |

いずれも通常の実ファイル（チャンク数十MB以下、PCHK展開後数百KB程度、値約268個）には十分な余裕のある水準である。

### バリデーション

- NISIメタデータの必須フィールド（`name` / `vendor` / `device_type`）が空文字列でないこと
- NICAパラメータの`id`が各配列内で重複していないこと

違反時はfail-fastでエラーとする。

## 理由

- **zipボム防御の決定版は`take()`**: 展開後サイズを先験的に知る方法はないため、「上限までしか読まない」方式が唯一確実である。50MBを超えて読めた時点で不正ファイルと判断する。
- **100,000という値数上限**: 正常系が約268個であることから3桁以上のマージンがあり、値数によるリソース消費攻撃を実質不可能にする。
- **fail-fast原則**: 不正入力は解析の早い段階で拒否することで、CPU・メモリの無駄な消費を最小化する。
- **意味的バリデーションの追加理由**: 「空のname」「重複したパラメータid」のような異常は、パーサーの構文解析だけでは検出できない。ライブラリの利用者にこの検証を委ねると、利用者ごとに品質がばらけるため、パーサー側で保証する。

## 影響 / 結果

- 悪意ある（または破損した）ファイルに対し、パーサーはクラッシュ・ハングではなく`ParseError`を返す。proptestによる「任意バイト列でパニックしない」検証（[ADR 0005](0005-test-architecture.md)）と組み合わさり、頑健性がテストで担保される。
- 上限値は定数として明示されており、正当なファイルで上限に達するような将来の形式拡張があった場合は値の見直しが必要になる。
- 上限超過はすべてエラー応答であり、警告付きの続行や部分解析のモードは存在しない。これは[ADR 0003](0003-complete-byte-parse-policy.md)のfail-fast方針と一貫している。
- セキュリティ上の理由を含むエラーメッセージが返されるため、利用者は失敗原因を把握できる。

## 代替案

- **上限なし＋ストリーミング処理**: メモリ使用量を抑えられるが、無限ループや時間攻撃への対策にならず、PCHKの全値を構造化する要件とも相性が悪いため不採用。
- **圧縮率ベースのチェック（展開前サイズ×固定倍率で制限）**: 実測の圧縮率は約16倍だが、内容によって変動し、正当なファイルを誤って拒否するリスクがあるため不採用。絶対上限との併用も複雑さに見合わないと判断した。
- **タイムアウトによる防御**: パーサーライブラリにスレッドや時間管理を持ち込むのは責務過多であり、呼び出し側で制御すべき問題として不採用。

# 0002: 解析ライブラリの選定と依存関係管理方針

## 日付

2026-01（初期開発時に決定）

## ステータス

承認済み（Accepted）

## コンテキスト

.nksfファイルはRIFFコンテナ形式であり、チャンクは「4文字ID + サイズ + データ」で構成される。NISI/NICA/PLID/PCHKの各チャンクはバージョン番号に続き、MessagePackでエンコードされたデータを保持する。PCHKチャンクのプラグインデータはzlibで圧縮されている。したがってパーサーには次の機能が必要になる。

- RIFFコンテナの走査（チャンク列挙、シーク、パディング処理）
- MessagePackのデシリアライズ
- zlib展開
- エラー型の定義
- CLI引数のパース

これらを自前実装するか、既存クレートに委ねるか、どのクレートを選ぶかを初期開発段階で決定する必要があった。

## 決定

以下のクレートを採用する。

| 用途 | クレート | 選定理由 |
|------|----------|----------|
| RIFFコンテナ処理 | `riff 2.0` | RIFFチャンク列挙・読み取りの標準的な実装。自前でのオフセット計算を回避 |
| MessagePackデシリアライズ | `rmp 0.8` + `rmp-serde 1.3` | `rmp`で低レベルな値読み取り、`rmp-serde`でserde派生構造体への直接デシリアライズを実現 |
| zlib展開 | `flate2 1.1` | Rustにおける事実上の標準。PCHKの圧縮データ展開に使用 |
| serde派生 | `serde 1.0`（derive feature） | チャンク構造体のデシリアライズ定義。CLI側のJSON出力でも再利用される |
| エラー型 | `thiserror 2.0` | `ParseError`列挙型の定義を簡潔にし、表示メッセージも一元管理 |
| CLI引数 | `clap 4.5`（derive feature） | `-o/-d/--jsonl/--overwrite`等のオプション宣言を構造体で記述可能 |

また、依存関係の管理ルールとして**Cargo.tomlを直接編集して依存を追加しない**ことを定める。追加は必ず `cargo add`（開発依存は `cargo add --dev`）で行い、最新互換バージョンの選択と Cargo.lock の整合をツールに委ねる。

## 理由

- **車輪の再発明の回避**: RIFF・MessagePack・zlibはいずれも仕様が確立しており、成熟したクレートが存在する。バイナリ解析コードを自前で書くと、境界ケース（奇数チャンクのパディング、MessagePackの可変長整数など）のバグ リスクが増す。
- **serdeエコシステムとの整合**: `rmp-serde`により「MessagePack → 構造体」を宣言的に書ける。構造体には`Serialize`も導出されるため、CLI側で同一の型をJSONへ出力できる。
- **`rmp`と`rmp-serde`の併用**: PCHKのように「連続するMessagePack値のストリーム」を読む部分では`rmp-serde`の構造体マッピングが使えない場面があるため、低レベルAPIも併せて採用した。
- **thiserror**: アプリケーション向けのエラー定義として定着しており、`#[from]`によるIO・デシリアライズエラーの変換が自然に書ける。
- **cargo addルール**: 手動編集によるバージョン指定ミスやlock不整合を防ぐ。レビュー時にも「どのコマンドで追加されたか」が追跡しやすくなる。

## 影響 / 結果

- `lib/Cargo.toml` の `[dependencies]` は riff / rmp / rmp-serde / serde / serde_json / thiserror / flate2 で構成され、解析に不要な依存は持ち込まれていない。
- テスト用ライブラリ群（rstest, insta 等）は別途dev-dependenciesとして導入しており、その選定は[ADR 0005](0005-test-architecture.md)に譲る。
- 依存追加はすべて`cargo add`経由で行われる運用となり、Cargo.lockの差分が依存変更の正確な記録になる。
- クレート選定の更新が必要になった場合（例: riffクレートのメンテナンス停止）、本ADRを廃止（superseded）して新たなADRを発行する。

## 代替案

- **RIFF/MessagePackの完全自前実装**: 依存をゼロにでき学習効果はあるが、境界ケースの検証コストが高く、本プロジェクトの目的（.nksfの全バイト解析）から外れるため不採用。
- **`serde_json::Value`ベースの統一的な扱い**: 全チャンクを汎用Valueとして読む案。型安全な構造体アクセスが失われ、呼び出し側での検証負担が増えるため不採用。
- **手動編集によるCargo.toml管理**: 差分の意図が不明瞭になりやすいため不採用（`[[bench]]`やprofile設定のような`cargo add`で表現できない項目を除く）。
